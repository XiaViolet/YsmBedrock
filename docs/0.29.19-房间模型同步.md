# Windows 原版房间模型同步 · 0.29.19

## 安装和使用

三台电脑都安装同一预览包，将包里的 `mods/YsmBedrock` 合并到各自的游戏实例。房主正常打开世界。访客仍使用好友邀请、好友列表或局域网入口。模组在原版游戏连接上协商，正常路径无需填写地址、开放其他端口或启动 Python 程序。现有为指定外部服务器配置的旧 `relay.json` 仍可使用。此版本的原版三人房间实机验收待完成。

按 **Alt+Y → 联机玩家** 可打开共享文件夹、房间规则、重读设置，查看其他玩家的接收或显示状态。房主可在此切换自动接收、拒绝某位玩家当前的模型，以及接收访客主动开放的其他模型。拒绝项可在规则文件中撤销。已屏蔽的玩家可恢复显示。

| 想做的事 | 操作和结果 |
|---|---|
| 让别人看见身上的模型 | 直接穿戴本地模型。支持的原包随当前选择登记。房主默认接收并向其他访客分发。其他人仅取得显示缓存。 |
| 房主公开其他模型 | 只将想公开的包或源模型子目录放入 `mods/YsmBedrock/room-share`，或在规则中填写本地模型库下的相对路径。点“重读共享设置”。房间成员会后台缓存这些模型。 |
| 访客主动分享未穿戴的模型 | 使用同样的共享文件夹或清单并重读设置。房主在“联机玩家”中点“接收分享”后，才会获取并公开该条目。 |
| 试穿或收藏 | 模型库里点击公开条目会提升下载优先级。显示下载提示时，完成后再次点击即可预览。预览底部的“穿戴”仅应用房间模型，“收藏到本地”将经过校验的原始包复制到自己的模型库。刷新模型库可见。 |
| 暂停分享或拒绝当前模型 | 房主关闭自动接收、拒绝对应模型或收紧规则，远端退回原版外观。取消目录共享时，还需考虑该模型是否正由成员穿戴并符合“自动接收当前模型”规则。 |

首次启动会在模组目录生成 `room-sync.json`。以下为默认配置。文件夹名、展示名和文件名不充当权限键。

```json
{
  "auto_receive_current": true,
  "shared_only": false,
  "shared_models": [],
  "denied_content_keys": [],
  "bytes_per_second": 262144,
  "cache_mib": 512
}
```

- `auto_receive_current` 控制是否接收访客当前使用的模型。`shared_only` 限制为显式公开或房主接受的模型。`denied_content_keys` 具有优先权。拒绝按钮会把相应内容键写入此文件。
- `shared_models` 只接受本机 `models` 内的模型路径，例如 `["角色/模型A.zip"]`。共享根也可使用独立的 `room-share` 目录。每端显式清单上限 64 项。加入房间时私人模型库不会作为目录发送。
- `bytes_per_second` 是模型文件分块的限速，默认每端每方向 256 KiB/s，可设 16 KiB/s 至 4 MiB/s。控制消息单独限队列。原版移动、区块和语音等使用游戏现有连接。
- `room-cache` 是可回收的房间缓存，默认 512 MiB，可设 128–8192 MiB。已验证的本地相同包也可复用。当前使用及本机明确提供的包会固定，空间不足时下载失败并保留可见外观。收藏文件使用 SHA-256 命名，存入 `models`。已收藏到他人本地的文件无法随房主日后的撤权收回。
- 支持现有导入器能读取且允许分发的 ZIP、二进制 YSM 和源目录。文件包逐字节传输。源目录传输时将实际引用的原始资源打包，作者文件保持原样。会话授权目录沿用权限限制；现有二进制 UV、姿态或材质兼容问题不由网络层修正。Windows 客户端与 Java YSM 客户端使用各自的联机协议。

## 源码基线

0.29.18 已有本地目录／ZIP／二进制导入、模型库、玩家动画播放器、远端皮肤替换、连续换装变量及一次性动作事件。原有联网实现按 `relay.json` 中的服务器地址匹配，通过外部 HTTP 服务交换状态并取文件，已有代码和离线回归可以沿用。该入口无法把普通房间内客人 A 的私有当前模型自动转发给 B。本版复用原导入、动画和皮肤实现，新增原版连接通道、房主授权、双跳文件流和缓存。此前其他测试实例或公开服务器上的结果不能证明本版好友房间已经通过实机验收。

## 实现位置

| 模块 | 位置及行为 |
|---|---|
| 原版连接和双向探针 | `src/NativeRoomTransport.cpp`、`RoomTransportProbe.h`、`RoomTransportQueue.h`。可选数据包 `ysm:room` 版本 1，在 client/server 两端注册。检查接收方能力，完成带连接随机数的 Hello/Ack/Confirm/Ready 后传业务数据。绑定原版连接、子客户端和玩家身份，回调只把有界数据放进邮箱。内置服务端和本地玩家走不同入口。 |
| 房主分发与协议 | `src/RoomProtocol.cpp`。协议携带房间、成员连接代次、模型选择修订、事件序列、模型格式和两种内容标识。房主决定权限及提供者，客人只和房主交换。分块 16 KiB，每个完整包上限 128 MiB。包损坏、失联、撤权及重复请求有独立处理。 |
| 文件、缓存和授权 | `src/RoomAssets.cpp`、`ModelPack.cpp`、`ContentHash.cpp`。SHA-256 校验传输字节，解析器再核对实际内容键和格式。暂存、原子发布、已使用资源固定、容量回收、显式收藏和本地匹配均在受管路径内。网络输入使用更严格的文件、解压、JSON 和模型几何预算。 |
| 调度与生命周期 | `src/NativeRoomSync.cpp`。串行 worker 维护房间状态，重型发布、收件校验使用有界后台作业。按控制、可见玩家当前模型、其他当前模型、手动选择、后台共享库排序。取消及跨世界返回的旧任务不能应用到新房间。未穿戴共享模型仅缓存，不建立远端动画实例。 |
| 角色显示 | `src/NativeModelRelay.cpp`、`SkinRuntime.cpp`。后台准备完成后再次比对世界、玩家、实体实例、选择、纹理和文件摘要。游戏线程完成纹理上传和绑定才发布可绘制角色。使用同一模型与贴图的玩家可共享解码模型，各自保留动画状态与事件游标。缺失或失败时继续绘制原版玩家。 |
| 控制入口 | `src/Mod.cpp`、`YsmUiLayout.cpp`。共享、规则、拒绝、接收以及收藏入口使用原有模型库界面。 |

## 已取得的证据

发行 ZIP 的 `verification` 与工程的 `build/verification/room-0.29.19` 包含测试输出。三节点的网络投递由内存测试端代替，模型、解析器、缓存、房主与访客的 worker 均使用生产代码。

- 未修改的绘梨衣原包，787,896 字节，从 A 到房主、房主到 B 各 49 个协议分块。本轮另外两套模型分别为 SignedFaceLab 和白色大肥鱼二进制 YSM（650,368 字节、来源版本 32）。三端六个远端模型均逐项通过磁盘 SHA、生产解析、所选纹理及角色状态检查。房主撤权后视图失效，恢复授权使用原缓存，新增分块数为零。见 `native-room-integration.txt`。
- 协议回放覆盖同名异内容、多人同模型不同动作、迟加入与重连、旧包乱序、缓存命中后拒绝真实文件请求、损坏、超时、后台下载时提权、异步校验期间传送动作。见 `protocol.txt`。
- 文件回放覆盖绘梨衣 ZIP 和白色大肥鱼 YSM 的两跳落盘、手动收藏及文件校验。作者包前后哈希相同。见 `assets.txt`。
- `transport.txt` 记录 SDK 和握手检查、尝试建立隔离正版游戏实例的结果。生产者→房主→访客的原版网络回调、游戏中的六个角色画面、实际好友邀请和游戏中的性能数据仍需实机验收。其他第一／第三人称、动作和换装保留原入口，本批验证范围见 `regression.txt`。

## 已知边界

经验证、仍在使用的同模型与同贴图可复用静态解码结果。不同贴图及每名玩家的游戏皮肤绑定仍有独立开销。后台校验完成前不会将新文件用于绘制。首次重开大文件缓存或核对私有模型库命中时，磁盘校验可能占用串行同步 worker，期间已显示角色仍沿游戏渲染线程运行。文件接收后的重型校验可以并行于控制消息。模型准备连续失败三次会保留原版外观及失败原因，重新选择或重进会话可再试。

## 三台 Windows 客户端的实机复验

1. 在三台有独立游戏身份的客户端安装相同版本。各建独立测试实例及新世界，将三份不同且允许分享的原包分别放入房主、A、B 的测试模型库。A 独有绘梨衣。使用新测试缓存目录或新实例即可，无需操作原有存档。需要采样时，在三端模组目录各建空文件 `room-metrics.enable`，随后启动游戏。
2. 在同一 LAN 通过原版入口加入，先由房主与 A 入房。核对加载器日志中注册、房主确认 A、A 收到 READY。穿戴三套模型，B 稍后加入。三端分别截下另外两人的角色，记录模型、贴图、一个独立换装和一个持续动作。缺包期间及下载失败时应能看见原版角色。
3. 在 B 无绘梨衣原包的情况下观察 A → 房主 → B。核对两个接收端 `room-cache` 中原始字节的 SHA-256，保留 B 看见 A 的画面。A 连续切换两次并换装，确认最终模型及外观。两人改用同模型，分别执行不同动作，检查相互独立。
4. 房主开放大型后台包，下载过程中让另一玩家进入视野并换到缺少的模型。另测缓存命中、同名异包、撤权、离开重连、切换世界和手动收藏。记录期间的客户端日志、世界和身份对应、UI 状态、六个方向的画面。分别跑一次空闲与传输场景，用相同视距和图形设置比较。
5. 在两处不同外网的设备上用原版好友邀请重复前述流程。保留房主和两名访客各自的证据。LAN 与跨网结果分别记录，每个参与者收到的其他两名玩家分别核对。
6. 采样文件 `room-metrics.jsonl` 约每秒一行，上限 4 MiB。字段包含帧间隔 p50／p95、进程工作集、发给传输层与收到的模型业务字节、已绑定人数，以及访客能取得的游戏连接延迟。字节计数不包含原版游戏数据。完成后移除测试实例的采样标志。若没有有效延迟样本，记录为空。

开发者可用 `py -3 -X utf8 -m unittest discover -s tests -v` 跑现有回归，`tests/run_room_protocol.ps1` 跑有界协议重放，`py -3 tests/run_native_room_integration.py --help` 查看真实 worker 三节点测试所需的构建目录、原包和可选二进制样包参数。构建方式、产物哈希见 `verification/build.txt`。

本机没有三套可用于隔离测试的独立正版身份。尝试从本地已安装的 GDK 包建立独立测试配置时，启动器要求交互登录并返回 `ERR_AUTH_INTERACTION_REQUIRED`。本轮没有操作正式游戏实例或个人世界，也没有测得可对外报告的 LAN／跨网延迟、游戏帧时间或工作集。
