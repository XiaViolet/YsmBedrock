# 0.29.15 复杂模型性能复验

基线为已发布的 Windows 基岩版 YSM 0.29.14。本轮沿用同一游戏版本、加载器和原包，分别观测游戏帧率、动画逻辑和原生骨骼绑定。

## 改动和依据

| 环节 | 旧版开销 | 0.29.15 行为 |
| --- | --- | --- |
| 游戏中的模型菜单 | 菜单关闭时仍在客户端 tick 构造模型目录和描述，枚举动作，并为每个作者控件拷贝私有 Molang／物理状态 | HUD 持续接收当前模型、贴图和纸娃娃设置。完整菜单在打开时刷新。首个新快照到达前保留转盘数字快捷键，并按打开批次丢弃过期快照 |
| 关键帧求值 | 纯数字的位移、旋转和缩放也逐轴经过通用求值入口 | 编译时识别有限数字，保留 Molang 的步数消耗、每轴的 `this` 和预算不足时的回退。含查询、物理或脚本的通道继续逐次求值 |
| 控制器混合 | 正常播放也为骨骼通道构造临时退场数据，重复以字符串查找相同骨骼 | 仅在退场时记录淡出进度，顺序合并已排序的骨骼通道，保留混合顺序和下层姿态 |
| 原生骨骼绑定 | 同一骨架在多条判断与绘制路径重复按名查找 | 复用已解析的绑定，但每次核对实际名称、数量和顺序。换模、重排及错配都会重查。绑定缓存不持有基岩版临时数组的地址 |
| 材质绘制 | 整个网格采用同一种作者材质时，仍构造每骨骼的材质分组 | 同一材质直接提交原有骨骼调色板。颜色、透明度、发光、裁切或其他属性有差别时仍走分组绘制 |

这些策略均在共用运行时生效。作者表单的观察仍使用私有上下文，实时姿势、首帧事件、动作时间或纸娃娃更新频率沿用原语义。

## 对照 Java 和社区实现

固定 Java 源码的 `AnimatedGeoModel` 准备有序骨骼与属性，渲染接口接收已准备的模型状态。其原生实现还可依据可见骨骼更新绘制任务。基岩移植的逻辑姿势仍是以骨骼名为键的 `std::map`，本轮只消除了若干重复查找与临时容器。CPU 动画开销仍会随活跃通道和脚本调用量增加。[Java 骨骼模型](https://github.com/YesSteveModel/YesSteveModel/blob/15c2c25f5b50f54ee099bc474483dc4b588d956d/src/main/java/com/elfmcys/ysm/geckolib3/model/AnimatedGeoModel.java) · [Java 渲染入口](https://github.com/YesSteveModel/YesSteveModel/blob/15c2c25f5b50f54ee099bc474483dc4b588d956d/src/main/java/com/elfmcys/ysm/geckolib3/geo/IGeoRenderer.java#L40-L47) · [原生任务构建](https://github.com/YesSteveModel/YesSteveModel-Native/blob/907d1c653b7eb85ee92ee11305134408300797f8/modules/gfx/src/renderer/model_state_impl.inc#L198-L211)

Ozz Animation 的采样上下文会跨帧保留已解压的关键帧。可借鉴的是按实例复用稳定数据，并在源数据更换时失效。本轮复用基岩版骨骼绑定，动态 Molang 查询与作者事件继续在对应时刻执行。Minecraft 社区的 ImmediatelyFast 则通过复用缓冲和批量提交减少即时绘制成本。本轮单一材质的快速路径借鉴这一原则。[Ozz SamplingJob](https://github.com/guillaumeblanc/ozz-animation/blob/master/include/ozz/animation/runtime/sampling_job.h#L43-L54) · [ImmediatelyFast](https://github.com/RaphiMC/ImmediatelyFast)

## 同一存档的游戏帧率

使用 Windows 基岩版 1.26.60.05、D 盘测试实例、同一份香奈美生贺 v1.0.3 原包和存档。角色第三人称原地待机，快捷栏选空的第九格，脚底坐标一致。FPS 按游戏 ProfilerLite 的整秒读数取中位数。帧回调率用窗口两端的累计渲染帧差除以实际秒数。动画逻辑耗时按窗口内的采样次数加权，从累计计时反算。

| 版本与天气 | 采样时长 | 游戏 FPS 中位数（范围） | 帧回调／秒 | 动画逻辑均值 |
| --- | ---: | ---: | ---: | ---: |
| 0.29.14 持续降雨，后台空闲复测 | 35.64 秒 | 29（27–29） | 28.90 | 22.16 ms |
| 0.29.15 持续降雨 | 36.43 秒 | 36（34–37） | 36.62 | 21.63 ms |
| 0.29.15 晴天，第一窗 | 36.50 秒 | 37（35–38） | 37.18 | 21.57 ms |
| 0.29.15 晴天，第二窗 | 36.45 秒 | 37（35–39） | 37.42 | 21.53 ms |
| 0.29.14 首次小雨，后台有回归任务 | 35.62 秒 | 27（23–28） | 27.34 | 22.85 ms |

主对照采用持续降雨和后台空闲的两个窗口，另行确认新旧 DLL 哈希。两端的原始雨量和归一雨量均为 1、闪电为 0，游戏截图尺寸均为 2048 × 1104，俯仰角相差约 0.46°，游戏时刻和日照自然变化。原生 FPS 的逐秒读数均值由 **28.58 升到 36.16（约 +26.5%）**。旧版首次小雨的雨量约 0.06，且后台有回归任务，仅列作参考。两版的模型表达式错误计数均为零。游戏截图、视角状态、DLL 哈希和按秒采样在工程的 `build/verification/perf-0.29.15/game`。过渡天气窗另标为 `discarded`。

同一新版实机还打开过模型库、纸娃娃、动作转盘和香奈美的“眼睛 → 设置”。作者的“瞳孔”滑杆显示当前值 0。关闭后约两秒内渲染帧和主动画更新均增加 76，暂停标记为假，表达式错误数为零。操作截图和恢复记录位于同一 `game` 目录。

## 三份原包的离线回放

`tools/benchmark_player.py` 依次调用 0.29.14 和 0.29.15 发布用的 `ysm-inspect.exe`，每轮交换新旧执行顺序。每包每版各 4 轮，每轮按 60 Hz 输入 176 帧待机、走动、持弓使用和切回的状态。丢掉每轮前 32 帧，每版每包保留 576 次 CPU 采样，计时排除模型载入和 GPU 绘制。附加的控件观测单独计时，测的是旧版在关菜单时仍执行的共享读取函数。新版关菜单时直接跳过该调用。

| 原包 | 动画回放中位数，旧 → 新 | P95，旧 → 新 | 作者控件数 | 单次读取全部控件的中位数 |
| --- | ---: | ---: | ---: | ---: |
| 香奈美生贺 v1.0.3 | 23.86 → 23.44 ms | 29.29 → 28.03 ms | 39 | 11.04 ms |
| 临战爱丽丝 | 8.76 → 6.49 ms | 11.69 → 8.83 ms | 34 | 34.98 ms |
| D蓝色大肥鱼 | 1.04 → 1.05 ms | 1.26 → 1.48 ms | 29 | 1.72 ms |

爱丽丝这段回放的 CPU 中位耗时降低约 26%。蓝色大肥鱼的中位耗时接近，P95 在本次采样中略高，尚未取得该模型的实机帧率。开销属于不同路径，不能直接把表中两列毫秒数相加再换算 FPS。

对三份原包另做同逻辑时刻和一次只读观察的 11 帧逐字段比较。完整骨骼姿势、骨骼材质状态、作者变量、控制器、时间线游标、声音／粒子与同步事件均一致。表达式运行失败计数均为零。原包树哈希、两版程序哈希、逐次耗时和编译诊断在 `build/verification/perf-0.29.15/player-ab.json`。可用 `py -3 tools/benchmark_player.py 旧版检查器 新版检查器 原包目录 --output 结果.json` 复跑。

## 回归与剩余开销

用临战爱丽丝与香奈美原包的实际骨骼顺序，在同一机器、同一编译设置下交错回放 9 轮，每轮 90 次。临战爱丽丝 6,896 骨的绑定步骤中位耗时从 332.66 降到 28.73 微秒，香奈美 1,034 骨从 34.48 降到 4.35 微秒。稳定布局每次分别省掉 20,688 和 3,102 次名称查找。绑定步骤的数字只含 CPU 查找与校验。

最终发布用二进制通过 951 项自动测试。新增用例覆盖了有限步数预算（1、2、3 步）、表达式出错后采样、同通道退场及只读观察。

独立 C++ 回归覆盖 8 项布局场景，含重排、同名数组换址、错配及恢复。555 组材质调色板含 500 组确定性随机输入，新旧路径选出的可见骨骼和材质一致。可在 x64 Native Tools 命令行从工程根目录运行 `cl /nologo /O2 /EHsc /std:c++20 /Isrc tests/native_render_regression.cpp src/BoneVisual.cpp`，再执行 `native_render_regression.exe`。

下一处值得细分计时的是香奈美原包的 `parallel3`。该片段的声明中有 726 处绝对骨骼枢轴查询、366 处一阶物理调用，以及作者的四元数运算。这些是代码出现次数。现有阶段计时尚不能分摊每种调用的实际耗时。基岩版脚本调用仍会在热路径检查签名与参数并构造实参数组，后续应先计量，再决定预绑定哪些调用。绝对骨骼枢轴本身已有单轮缓存。

### 仍能复现的诊断

- 香奈美的 `pre_parallel6 → segment_6826_c → rotation[2]` 中，最外层 `3*(` 没有闭合。两版检查器都给出 `Molang at 80: Expected )`，该轴回退到 0。
- 临战爱丽丝的 `parallel1 → timeline["0"][40]` 在给 `v.MHair_p10dot` 赋值时缺右括号。该包逐条执行时间线脚本，因此当条赋值回退，后面的发梢弹簧仍会读取这个变量。两版编译诊断均为 `Molang at 79: Expected )`。该异常在 Java 2.6.5 正式客户端产生的具体外观尚未实测。
- 两个基岩版本进测试世界时均出现过资源或行为包加载提示。世界资源包和行为包清单为空，内容日志未给出失败包标识，YSM 的源包解析和几何、贴图应用均有成功记录。现有日志不足以定位提示来源。
