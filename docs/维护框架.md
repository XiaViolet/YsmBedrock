# YsmBedrock 维护框架

这个工程维护的是 Java YSM 模型在基岩版上的运行行为。另一位作者用不同的模型名、骨骼名和资源名表达同一条原版规则时，也应该受益于同一次修复。

## 代码怎么分工

[构建配置](../xmake.lua)里的 `core_sources` 同时编入游戏 DLL 和 `ysm-inspect`。导入、动画采样、脚本求值和实体匹配已有共用实现。游戏 DLL 还编入 `Mod.cpp`、`AnimationRuntime.cpp`、`SkinRuntime.cpp` 和 `Native*.cpp`，负责接入基岩版。沿用这两个入口即可。以下分工用于定位和修改现有代码。

| 从哪个问题开始 | 先看哪里 | 这一层负责什么 |
| --- | --- | --- |
| 同一个原包在两端读出的资源不同 | `ModelPack`、`LegacyBundle`、`ModelLibrary` | 保留作者声明的动作、资源标识、引用和缺省值。记录哪条引用未解析，保留 Java 对该情况的处理语义。 |
| 包已读入，动作、骨骼或事件选择不同 | `AnimationControllers`、`CodedAnimationPlayer`、`AnimationSampler`、`Molang` | 用同样的实体输入、时间和模型数据复现 Java 的控制器选择、姿态和事件。离线回放和游戏走同一条规则。 |
| 离线给对输入能重现，游戏里触发条件不同 | `EntityQueries`、`JavaVanillaInputs`、`AnimationRuntime`、对应 `Native*` 接口 | 确定查询的是谁、在哪一刻取值、单位是什么。区分查询对象、持有者和发射者，保留当前主体。 |
| 投射物或载具选错模型、纹理或动画 | `ModelTargets.cpp`、`ReplacedModelAssignments`、`NativeReplacedResources` | 前两处检查作者匹配规则和替换归属，再查游戏中的实际对象及其资源绑定。控制器选中后沿用动画求值链。 |
| 姿态或特效事件正确，画面与声音仍不同 | `BoneVisual`、`ModelPreview`、`ModelParticles`、`ModelAudio`、`NativeRenderBindings`、`NativeModelParticles`、`Mod.cpp` | 对照姿态和事件数据，再查原点、骨骼定位、贴图、玩家视角、声音实例或原生提交。明确问题出现在菜单、世界或两者。 |
| 本人正常，旁观者、换模或重连后异常 | `AnimationRuntime`、`ModelRelay`、`NativeModelRelay`、`MolangRoamingSession`、`Mod.cpp` | 追踪模型与实例归属、状态快照、一次性事件和旧实例清理。菜单操作从 `YsmUi` 追到实际应用动作的入口。 |

扩充平台接口时，把基岩版对象读写放在游戏侧，把 Java 的判定规则放在现有共用模块中。动画时间、实体位置或资源 ID 穿过这条边界时，用现有数据结构传递。状态跟着实际对象走，例如一把已经投出的三叉戟有自己的飞行状态。切换手持物、切换模型和实体消失时，分别检查哪些状态应保留、哪些应释放。渲染一帧可能多次取姿态，同一个时间线事件的派发次数要单独验证。

## 从一个模型的症状找到通用修复

1. **固定对照。** 在[Java 功能对照](Java功能对照.md)找到相应行为，沿用指定的 Java 正式版。在两端加载同一份原包，记录动作、视角、触发步骤和首次出现差异的时刻。
2. **找到第一处差异。** 顺着“作者声明 → 导入结果 → 实体和时间输入 → 控制器、姿态或事件 → 游戏内呈现”对照。只记录与症状相关的值。前一步已经不同，就先修这一层。
3. **锁住通用规则。** 用可重放的最小用例覆盖第一处差异，尽量先在旧实现上观察到失败。换一个作者资源 ID 或另一份结构相同的原包复验，检查修复是否依赖样例名字。保留原始模型供实机回归。
4. **按行为交付。** 跑受影响分组。可见、可听或多人行为分别保留对应的游戏证据。把结果填回现有功能对照表，同一行含有不同验收结果时拆成具体行为。沿用表内的五种状态，写清未测条件和下一步。

例如，模型自带粒子在三叉戟飞行时消失，可以依次比较两端的投射物匹配结果、当时选中的动作和播放时间、粒子事件的资源标识和次数，以及基岩游戏端采用的定位点与坐标。如果基岩版已经选中同一动作并产生同一事件，就从资源解析和绘制位置查起。再用一次普通投掷与一次忠诚返回区分事件跟着投射物还是玩家。这个例子给出排查顺序，实际预期由所选原包在 Java 的表现决定。

## 怎么跑回归

在含 `xmake.lua` 的工程目录执行。改过 C++ 时先重新编译，否则检查器会运行已有二进制。

```powershell
.\tools\build.ps1
py -3 tools/check_feature.py --list
py -3 tools/check_feature.py inputs animation entities effects
```

| 改动涉及 | 分组 |
| --- | --- |
| 包格式、资源库、贴图解码 | `import` |
| 动作、时间线、控制器、第一人称和装备动画 | `animation` |
| Molang、物理、模型函数、延迟事件 | `script` |
| 实体查询、宿主输入、天气 | `inputs` |
| 几何、骨骼、坐标和绘制 | `render` |
| 载具与投射物的匹配、归属和替换 | `entities` |
| 粒子与声音 | `effects` |
| 菜单、按键和模型选择 | `ui` |
| 联机、事件同步和跨会话状态 | `sync` |

可以组合分组，交叉覆盖的测试模块只运行一次。新增测试文件时，把模块加到[回归入口](../tools/check_feature.py)对应分组。已有构建可用 `py -3 tools/check_feature.py all` 全量发现测试。准备发布时，已有的 `.\tools\build.ps1 -Test` 会重新构建并运行完整回归。

## 怎样判断完成

| 要回答的问题 | 相应证据 |
| --- | --- |
| 修的是哪条 Java 规则？ | 正式版原包复现、可观察预期，以及能定位时的 Java 源码入口。 |
| 共用实现能正确求值吗？ | 最小回归的输入和断言，例如命中的替换目标、姿态值、事件 ID 与触发次数。 |
| 玩家实际得到相同结果吗？ | 在相同原包和条件下比较两端画面或声音。多人可见性由接收方观察，再记录必要的延迟或重连条件。 |

接手时从[Java 功能对照](Java功能对照.md)选一条未闭环行为，按影响原包的范围及现有复现条件排优先级。本轮记录只需写清行为、首个差异、修改入口、回归命令、实机证据和剩余条件。详细样例可参考[三叉戟验收](弓弩与三叉戟验收.md)与[动画时长和分组验收](动画时长与分组验收.md)。升级 Java 基准或基岩版客户端时保留原验证版本，优先重跑受影响的行为。
